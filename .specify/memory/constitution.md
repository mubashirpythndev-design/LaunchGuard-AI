# LaunchGuard AI Constitution

> Non-negotiable principles. Every spec, plan, task, and line of code must comply.
> Prompt to run first: `/sp.constitution` (or paste this file as the agent's project rules).

**Normative language**: MUST / MUST NOT are binding and are verified at the gates in section 5
and section 7. SHOULD marks a default that may be departed from only with a written
justification recorded in the plan's Complexity Tracking table.

## 1. Product Identity

LaunchGuard AI is an **AI co-pilot for low-cost rocket safety inspection**. It inspects rocket
hardware and launchpad conditions from images, video, and webcam input, and returns a launch
decision of **GO**, **HOLD**, or **NO-GO**, together with the reasons and recommended actions
behind that decision.

*Rationale:* the product's value is the decision and its justification, not the detection
itself. Every other section in this constitution exists to keep that decision trustworthy.

## 2. Safety Principles (Highest Priority)

These five principles outrank every other principle in this document. When a safety principle
conflicts with any other principle, feature velocity, or delivery pressure, the safety
principle wins.

### I. Deterministic Decisions

The GO / HOLD / NO-GO verdict MUST be computed by a deterministic rule engine from structured
findings. The LLM MAY explain findings and recommend actions; it MUST NOT upgrade a verdict —
for example, it MUST NOT turn HOLD into GO. The LLM MAY only agree with the rule engine or
escalate it to a more conservative verdict.

*Rationale:* a probabilistic model must never be able to talk a range into a launch. A
verdict that can be argued upward is not a safety control.

### II. Fail Safe

Any module that errors, times out, or returns a confidence below the documented low-confidence
threshold MUST yield `severity: "warning"` and MUST NOT yield `ok`. Missing mandatory checklist
inputs MUST produce `HOLD`.

*Rationale:* silence is the most dangerous failure mode. A check that could not run is
indistinguishable from a check that found nothing unless the system says so explicitly.

### III. Explainable Findings

Every finding MUST carry: module, check id, severity, human-readable message, confidence in the
range 0–1, measured metrics, and — when the finding is visual — an annotation overlay. A
finding missing any of these fields MUST NOT be rendered as, or admitted into, a decision.

*Rationale:* a verdict a reviewer cannot audit is indistinguishable from a guess, and defeats
the purpose of a safety co-pilot.

### IV. Honest Uncertainty

User-facing wording about unverified visual inference MUST be hedged — "appears", "possible" —
and MUST NOT assert certainty the CV pipeline did not produce. The product MUST NOT claim
certification, regulatory approval, or guaranteed safety. A persistent disclaimer reading
*"Decision-support tool. Not a replacement for certified range safety."* MUST be visible
wherever a verdict is displayed.

*Rationale:* the intended user is a rocket operator under time pressure. Overstated confidence
is a direct safety hazard, and honest framing protects the user from over-trusting the tool.

### V. Vision Proposes, Agent Coordinates

The agent MUST orchestrate CV tools and MUST NOT re-implement their detection logic, bypass
them, or invent measurements. Every numeric claim that reaches a report MUST trace back to a
tool result.

*Rationale:* the agent is an orchestrator, not a sensor. An invented measurement is
indistinguishable in the UI from a measured one, and violates Principle III.

## 3. Architecture Principles

### I. Two Deployables, One Contract

The system MUST consist of exactly two deployables bound by one generated contract:

- `apps/web` — Next.js (App Router) + TypeScript (`strict: true`).
- `apps/api` — Python 3.11 + FastAPI + OpenCV + YOLOv8 + agent.

The contract MUST live in `packages/contract` and be generated from the API's OpenAPI document
into TypeScript types and Zod schemas. The frontend MUST NOT hand-write API types.

*Rationale:* a hand-written frontend type drifts from the API silently and becomes a source of
wrong verdicts; generation makes drift a build failure instead.

### II. CV Lives in Python Only

Core computer-vision logic MUST live in `apps/api` only. OpenCV.js or any equivalent
browser-side CV is prohibited. The browser MUST limit itself to capture, upload, and render.

*Rationale:* one implementation, one set of fixture-tested results, and identical behaviour
between the demo and the deployed product.

### III. Agent Tools Are Pure Functions

Every agent tool MUST be a pure function with the shape `(input) -> Finding`, MUST have typed
input and output, and MUST be unit-tested against fixture images.

*Rationale:* purity is what makes a safety check reproducible, order-independent, and testable
without a running range.

### IV. Streaming First

Agent progress MUST be streamed to the UI over Server-Sent Events so that each checklist step
animates live as it is evaluated.

*Rationale:* a single opaque spinner hides which step failed; live progress is what makes the
decision explainable while it is being produced.

### V. Stateless CV, Stateful Runs

CV functions MUST NOT hold cross-request state. Runs, findings, and reports MUST persist in
SQLite behind SQLAlchemy so the store can be swapped without touching CV or agent code.

*Rationale:* statelessness keeps CV reproducible; a swappable store keeps the hackathon's
SQLite choice from becoming a future migration crisis.

## 4. Frontend Principles

### I. Type Safety

TypeScript MUST run with `strict: true`. The `any` type is prohibited. `@ts-ignore` is permitted
only when accompanied by a comment stating the specific reason it is required.

*Rationale:* the UI is where a verdict is finally read; type holes are where an unsafe value
becomes a confident-looking one.

### II. Composed Primitives

UI primitives MUST come from shadcn/ui, installed via the CLI into `components/ui`. Hand-rolled
buttons, dialogs, tabs, tables, and toasts are prohibited.

*Rationale:* one accessible, consistent primitive set keeps contrast and focus behaviour correct
by default instead of per-feature.

### III. Atmosphere Without Compromise

Interactive and animated flourishes MUST come from React Bits, installed via the shadcn CLI
registry into `components/react-bits`, and MUST be confined to atmosphere: background effects,
hero text, counters, and spotlight cards. React Bits MUST NOT appear on the decision-critical
path — the verdict, the finding list, severity indicators, and the disclaimer — where motion or
reduced opacity could impair legibility.

*Rationale:* atmosphere earns the demo its polish; legibility earns the operator their safety.

### IV. Theme and Styling

Styling MUST use Tailwind CSS with CSS variables following the shadcn theme. The default theme
MUST be dark, mission-control. A light theme is optional.

### V. Data And State Discipline

Server data MUST be fetched with TanStack Query. Forms MUST use React Hook Form with Zod. State
MUST be local React state, with Zustand permitted only for the live-monitor store.

*Rationale:* one store for one problem. A global store that absorbs everything makes the
decision path impossible to reason about.

### VI. Accessibility

WCAG AA contrast MUST be met. Decision state MUST be conveyed by text, icon, and colour
together, and MUST NOT rely on colour alone. `prefers-reduced-motion` MUST be respected by
disabling React Bits animations.

*Rationale:* colour-only signalling is unreadable to a meaningful fraction of users, in a
context where misreading GO as NO-GO has real consequences.

### VII. Server-First Rendering

Components MUST be React Server Components by default. `"use client"` MUST be added only where
interaction or browser APIs are required.

## 5. Quality Bar

### I. Lint And Type Gates

`apps/web` MUST be linted with ESLint and formatted with Prettier. `apps/api` MUST be linted
with Ruff and type-checked with mypy. CI MUST pass before a change is considered complete.

### II. Test Obligations

`apps/web` MUST be tested with Vitest and React Testing Library, and with Playwright providing
at least one end-to-end test per demo scenario. `apps/api` MUST be tested with Pytest against
fixture images for the 3 demo scenarios. Every CV module MUST have a fixture test covering at
least one passing image and one failing image.

*Rationale:* in a safety tool, the failing case is the case that matters. A CV module tested
only on images it passes is untested.

### III. Secrets

No secrets may be committed to the repository. `.env.example` MUST be kept current.
`OPENAI_API_KEY` MUST remain server-side only and MUST never reach the browser bundle.

### IV. Commits

Commits MUST be small and reviewable, following Conventional Commits. One task equals one
commit.

## 6. Scope Discipline (Hackathon)

### I. MVP Boundary

The MVP is exactly 3 modes — Pre-Launch Inspection, Launchpad Monitor, and AI Safety Report —
and 3 demo scenarios producing GO, HOLD, and NO-GO respectively.

### II. Deferred Work Stays Out

Items classified as future scope — thermal imaging, drones, telemetry, and the digital twin —
are out of scope and MUST NOT leak into MVP code, UI, or copy. Any spec that touches them MUST
list them explicitly as deferred.

### III. Vertical Slice Over Breadth

A working, demoable vertical slice MUST be preferred over breadth. Under time pressure, polish
MUST be cut before safety logic.

## 7. Definition of Done

A task is done only when every one of the following holds:

- The code compiles with no type errors.
- Lint passes.
- The tests covering it pass.
- It is visible and usable in the UI, if user-facing.
- It matches the acceptance criteria in `spec.md`.

Failing any condition means the task is not done, regardless of schedule pressure.

## Governance

This constitution supersedes all other practices in the repository. Where an agent context file,
a template default, or a plan conflicts with it, this file wins and the conflict MUST be
corrected in the other artifact.

**Amendment procedure**

1. Run `/sp.constitution` and state the change together with a written rationale that names
   the affected principles and sections.
2. Assess impact against `.specify/templates/plan-template.md`,
   `.specify/templates/spec-template.md`, and `.specify/templates/tasks-template.md`.
3. Bump the version per the policy below.
4. Prepend a Sync Impact Report to this file recording the old and new version, added and
   removed sections, and the status of every dependent artifact.

**Versioning policy**

The constitution version follows semantic versioning:

- **MAJOR** — a principle is removed, redefined, or a hard constraint is relaxed. Downstream
  artifacts MUST be migrated in the same change.
- **MINOR** — a principle or section is added, or existing guidance is materially expanded.
- **PATCH** — clarifications, wording, and typo fixes that create no new obligation.

**Compliance review**

- The Constitution Check gate in `plan-template.md` MUST be completed before research begins
  and re-evaluated after design.
- `/sp.analyze` MUST classify any violation of a MUST-level principle as CRITICAL. Conflicts
  MUST be resolved by changing the spec, plan, or tasks — never by reinterpreting, diluting, or
  silently ignoring the principle. Changing a principle requires a separate, explicit
  constitution update, not a downstream edit.
- The gates in section 5 and the Definition of Done in section 7 are the merge gate. A change
  that fails either is not complete.
- Every deviation MUST be justified in the plan's Complexity Tracking table. Unjustified
  deviation is a review failure.
